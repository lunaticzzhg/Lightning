# 技术方案：本地平台与策略管理

- 需求编号：REQ-001
- 状态：阶段一已按新空库实现；实测与限制见测试报告
- 依据：[PRD](./prd.md) · [交互原型](./prototype.html)
- 方案日期：2026-10-23

## 1. 方案摘要

本机浏览器访问 Docker 中的管理台。页面调用同源 API；后端读取并静态校验策略包，将策略和不可变代码版本写入本地 MySQL。只有数据库提交成功，页面才显示“已导入，未运行验证”。阶段一不执行策略代码，也不接收或保存用户填写的参数值。

```text
本机浏览器 → 127.0.0.1:8000 → Web 页面 / FastAPI → MySQL
                                      ↓
                              静态校验 ZIP 与参数定义
```

职责按入口、业务、存储分开：`web/` 展示策略、版本和参数定义；`backend/features/strategies/` 决定上传、归属和去重；`backend/infra/` 连接 MySQL；`contracts/http/` 定义管理接口；`contracts/strategy/` 定义策略包和未来运行接口；`deploy/local/` 与 `scripts/` 负责启动、备份和恢复。不为回测、模拟或交易预建模块。

首期沿用 React + TypeScript、FastAPI、MySQL 8.4、Alembic 和 Docker Compose。Web 构建后由应用同源提供；MySQL 保存业务事实。应用端口只发布到 `127.0.0.1`，数据库不发布宿主机端口。Docker 文档说明指定该地址可把发布端口限制在本机访问范围内：[Compose 端口映射](https://docs.docker.com/reference/compose-file/services/)。

## 3. 策略包与接口

### 3.1 策略包合同

上传 ZIP；根目录至少有 `strategy.json` 与 `strategy.py`。`strategy.json` 声明格式版本、未来运行接口版本、名称与说明、市场、分钟周期、所需行情字段、代码入口、Python 环境、依赖和参数定义。市场用 `CN`、`US` 标识；周期以正整数分钟声明。阶段一只验证声明格式与支持范围，不承诺对应行情已经可用。

清单示例（字段与类型以 `contracts/strategy/` 的合同为准）：

```json
{
  "schema_version": 1,
  "interface_version": 1,
  "name": "双均线策略",
  "description": "根据分钟行情调整目标持仓",
  "markets": ["CN", "US"],
  "bar_interval": "1m",
  "required_fields": ["open", "high", "low", "close", "volume"],
  "entrypoint": "strategy:on_bar",
  "python": "3.13",
  "dependencies": [],
  "parameters": [
    {"name": "fast_window", "type": "integer", "required": true, "default": 5, "min": 1}
  ]
}
```

参数定义支持整数、小数、布尔值、文本、枚举，以及必填、默认值、数字范围和枚举选项。默认值也须符合自身规则；参数名不能重复，也不能用于存储券商密码或密钥。首期只接受声明 Python 3.13 的包；依赖清单可以声明所需软件，但上传时不安装或验证其可用性。技术合同固定入口 `strategy.py:on_bar(event)` 和 `interface_version`，为后续运行留出可识别边界。未来事件提供行情、只读账户状态和**该次运行固定的完整参数**；策略输出目标持仓。运行字段的具体含义在 `contracts/strategy/interface-v1.md` 固定后才能声明代码可运行；阶段一仅做静态检查，不导入或执行上传的代码。

上传先限制原包大小 10 MiB、文件数 100、解压总量 50 MiB，再拒绝损坏、加密、重复路径、绝对路径、`..` 和符号链接。校验清单、Python 语法与入口后，对**原始 ZIP 字节**计算 SHA-256。限制值属于首期实现选择，需用实际策略样例复核。FastAPI 的文件上传使用表单文件请求：[官方文件上传说明](https://fastapi.tiangolo.com/tutorial/request-files/)。

### 3.2 管理接口

`contracts/http/` 用 OpenAPI 3.1 维护管理协议，并生成前后端的传输模型；路由检查须与合同一致。阶段一只需：

| 操作 | 接口 |
| --- | --- |
| 列出策略、上传新策略 | `GET /api/strategies`、`POST /api/strategies` |
| 查看策略、上传其新版本 | `GET /api/strategies/{strategy_id}`、`POST /api/strategies/{strategy_id}/versions` |
| 查看代码版本、下载原始包 | `GET /api/versions/{version_id}`、`GET /api/versions/{version_id}/download` |
| 服务状态 | `GET /health/live`、`GET /api/status` |

版本详情返回所属策略、清单、时间、校验值及“已导入，未运行验证”状态。上传失败返回可理解的原因：格式错误、名称不符、重复或冲突、记录不存在、数据库不可用。浏览器不自行分配 ID 或版本号；无参数配置及修订接口。原包下载按保存的字节返回，不重新打包。

## 4. 数据与主要流程

| 记录 | 首期字段与约束 |
| --- | --- |
| 策略 | 平台生成的 UUID、名称、规范化名称、创建时间。名称去首尾空格后不区分大小写，规范化名称唯一。 |
| 代码版本 | 平台生成的 UUID、所属策略 ID、策略内递增版本号、原文件名、UTC 上传时间、清单、SHA-256、原始 ZIP 和状态。`(策略 ID, 版本号)` 与 `(策略 ID, SHA-256)` 唯一。 |

仅建立“策略 1→多 代码版本”。新建策略和首个版本、上传已有策略的新版本，均在一次数据库事务中完成；原包与版本记录同次提交，失败不留下半条记录。向已有策略上传时先确认包内名称与目标策略一致；完全相同的原包返回已有版本提示。并发上传依靠数据库唯一约束兜底。MySQL 时间字段统一存 UTC，接口返回带时区的时间，页面按本地时间展示。

**阶段一不建参数配置、配置修订或回测表。** 后续每次回测在提交时固定代码版本 ID、完整参数值、数据版本及其余运行输入；同一代码和参数可被多次运行引用，各次运行各有记录。这里不提前设计回测表或参数填写页面。

## 5. 本机部署与数据保护

`deploy/Dockerfile` 构建页面与 Python 应用；`deploy/local/compose.yaml` 启动应用和 MySQL 8.4。MySQL 使用持久卷；初始化由 Alembic 建表，应用只持有日常读写凭证。密码放在本机私有文件，不写入镜像或仓库。页面、API 和下载同源；后端校验 Host、写入来源与本次启动令牌。管理台没有远程关闭接口，启停由本机命令完成。预先取得所需镜像和依赖后，不联系服务器也能启动与使用。

备份命令先暂停写入，再一致性导出 MySQL，保存到 Docker 数据卷之外，并生成包含策略、版本、关联及原包 SHA-256 的核对信息。恢复只在独立 Compose 项目和独立卷中执行；校验一致才算可用备份。备份在同一块磁盘上无法防范整机或磁盘损坏，首期不做自动备份和管理台备份页面。

项目尚未上线，本阶段从空库安装；不设计旧数据迁移、旧版本兼容或跨版本升级回退。以后出现已交付版本时，再为具体版本制定升级方案。
