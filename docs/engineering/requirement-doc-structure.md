# 需求文档结构规范

## 结论

一项需求的文档按 **PRD → 架构设计（需要判断职责时）→ 技术方案** 推进。三份文档各回答一个问题：用户要得到什么、系统由谁负责、具体怎样实现。章节顺序固定；章节内只写本需求需要的内容。所有文档遵守根目录 `AGENTS.md` 的写作要求。

每份文档开头写需求编号、状态和依据链接。未确认的决定、未实测的结果如实标明。需求索引 `README.md` 只放目标、产物入口和关键变更，不复制正文。

## 表达形式

先用一两句话给出结论，再用适合的图表承载细节，避免连续的大段文字：

| 内容 | 优先形式 |
| --- | --- |
| 多个对象、规则、方案或需求编号的对照 | 表格 |
| 功能在现有系统中的位置、模块职责和依赖 | 架构图，画出边界、连接和最终以哪处数据为准 |
| 用户操作、数据处理的先后与分支 | 流程图 |
| 用户、页面、后端等多方之间的请求、响应和失败 | 时序图 |
| 页面交互和反馈状态 | 原型图，紧邻对应需求 |

图表旁写清结论、关键例外和待确认项。简单的一步操作用一句话即可；不要为了凑图表而画图，也不要只放图、不解释判断依据。图中术语与正文一致。

## 概念说明（所有文档通用）

无论项目领域和文档类型，都要让第一次接触项目的人，不靠口头补充也能理解核心概念及其延伸概念。只解释影响使用、判断或实现的概念；普通词语不凑术语表。按下面顺序说明：

| 要说明什么 | 写到什么程度 |
| --- | --- |
| 核心概念 | 它是什么、解决什么问题、包含什么、不包含什么；与容易混淆的概念有何区别。 |
| 关键属性 | 文档提到的每个关键属性是什么意思，给出取值或例子；说明它是用来识别、分类、描述，还是记录一次变化，以及能否修改。 |
| 延伸概念 | 如子类型、实例、版本、状态、事件或处理结果。说明它从哪个概念延伸而来、何时产生、与原概念是什么关系。 |
| 关系与变化 | 说明谁属于谁、谁依赖谁，以及必要的先后或数量关系；新增、修改、结束或异常时，哪些内容跟着变化。 |
| 贯穿例子 | 用同一个具体场景串起核心概念、延伸概念和关键属性，让读者能对照实际操作。 |

先定义概念，再在流程、原型和方案中使用同一名称。每份文档首次使用核心概念时，给出足够理解本文的简短解释；详细定义可链接到权威文档，不必整段复制。适合用表格或小图说明关系；简单概念用一句话即可。没有某类延伸概念时不硬造。未决定的含义或边界标“待确认”，不要让读者靠猜测补齐。

## PRD：用户要得到什么

PRD 从使用者要完成的任务出发，按下表推进。使用 [PRD 模板](../templates/prd.md)，固定“需求背景、需求术语、需求详述”三节，不另增章节。

| 步骤 | 必须做什么 | 输出结果（写入章节） | 进入下一步的条件 |
| --- | --- | --- | --- |
| 1. 定目的与场景 | 写清为什么做、给谁用、何时用、现在有什么限制，以及怎样算完成；选代表性场景和常见例外。 | **需求背景**：一句话目标、场景表和本阶段范围。 | 能从使用者角度说清任务和可见的完成结果。 |
| 2. 定概念与规则 | 从最终使用结果倒推本阶段要固定的核心概念、关键属性、关系和变化；用同一场景举例。 | **需求术语**：概念与属性说明、关系和例子。 | 影响行为的概念已明确；其余未定边界标“待确认”。 |
| 3. 写行为与验收 | 按使用顺序写主线和常见例外；多步操作先画流程图，再用 `R-xx` 写入口、行为、反馈和验收重点。 | **需求详述**：流程图（适用时）及编号需求。 | 每项主要需求都能对应场景和完成结果。 |
| 4. 设计交互与衔接 | 有界面时完成下方交互设计六步，把原型图放在对应需求旁；写清本阶段结果如何供后续使用，以及待确认项。 | **需求详述**：原型入口与截图（无界面时写“不适用”）、阶段衔接和待确认项。 | 主要路径与常见例外可走通；关键未知项没有被当作已确定。 |

PRD 写可观察的产品行为，不写数据表、接口路径或框架选型。

## 交互设计：默认简洁，按需展开

交互设计必须按以下顺序完成。每步都要留下对应结果；已有结果直接引用 PRD，新增结果用简短表格或图记在“需求详述”或原型说明中，不重复抄写。缺少前一步结果，不开始下一步。

| 步骤 | 必须做什么 | 输出结果 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 1. 定任务 | 从 PRD 提取使用者、使用场景、目标和常见例外，确定完成任务的主线。 | 场景清单和操作主线。 | 能说清用户怎样完成任务。 |
| 2. 分页面 | 按主线划分页面和关键状态，说明从哪里进入、怎样到下一步。 | 页面与状态清单、跳转关系。 | 主线和常见例外都有去向。 |
| 3. 定重点 | 逐页写明页面任务、主内容区（必须看的内容）和主操作（下一步最需要做的事）；主操作变化的状态分别写。若一页有多个争抢注意力的重点，先重新划分页面。 | 每页“任务—主内容—主操作”对照表。 | 每页及关键状态的重点明确。 |
| 4. 筛复杂度 | 逐页列出每个交互点，逐项判断谁在何时需要它、它帮助做什么判断或操作、能否由系统处理，以及不展示会有什么影响。无必要性就删除；有必要性再决定默认展示还是按需查看。 | “交互点—必要性—处理方式”取舍表；标出必须直接可见的风险。 | 每个交互点都有取舍结论；默认页面只留下当前任务必需的内容。 |
| 5. 画原型 | 按前四步设计默认、空结果、失败和完成状态，走通主要路径与常见例外。 | 可操作原型及与 PRD 需求对应的截图。 | 主要路径和常见例外能操作、能看到反馈。 |
| 6. 自查修正 | 以第一次使用者的视角走通所有关键状态，对照取舍表检查原型；后来增加或改变的交互点也重新判断必要性。核对重点、下一步、文案含义和风险提示，发现问题先修正。 | 逐项核对结果及修正后的原型。 | 原型中的交互点都能说明必要性；多余复杂度已去除，关键风险仍清楚。 |

主操作可以是查看、选择或提交，不必总是按钮。

默认页面先让使用者看懂当前结果和下一步操作。逐页检查信息块、字段及默认值、按钮、链接、状态、提示、文案、图表标记、表格列和展开项；默认、空、失败、完成状态都不能漏。取舍表至少记录“页面或状态、交互点、必要性、处理方式”，用途相同的点可以合并。

“可以折叠”“实现方便”或“以后可能有用”不是保留理由。系统能可靠处理的留在内部；没有依据、又会影响保存结果的选项不得预选。展示的数量、状态和判断也要有依据，不能确定时不写成确定结论。影响当前判断的风险直接展示。

| 情况 | 设计要求 |
| --- | --- |
| 页面初次打开 | 突出主要内容和主要操作；次要操作不与它争抢注意力，避免重复入口。 |
| 页面文案 | 一处只表达一类意思，不把数量、问题、权限等不同概念串成一条状态。先写用户需要的结论和下一步，再决定是否展示数字或原因；用符合当前场景的对象和单位，少用内部术语。每句话都要能回答“为什么现在要看到它”。 |
| 系统内部处理 | 可由系统可靠完成的解析、转换、校验等处理交给系统；页面展示使用者需要的结果和下一步，不要求其理解内部步骤或术语。确需人工决定时，说明影响并给出可执行的选择。 |
| 信息或表单较多 | 按使用者的判断顺序分步或分组。已确定的信息直接展示；只让使用者填写或确认尚不明确的内容。返回上一步时保留已填内容。 |
| 多条记录或数值需要对照 | 优先用表格对齐同类信息，只留判断所需的列。记录很多时先给摘要，再按需筛选或展开，避免一张长表占满页面。 |
| 缺口、疑点或使用限制 | 会影响当前判断的结论默认可见；详细原因和原始记录可以展开查看。不要为了页面简洁而藏掉关键风险。 |
| 空数据、失败和完成 | 说明发生了什么，并给出明确的下一步；不让使用者猜测是否已保存或还能做什么。 |

## 架构设计：怎样融入现有体系

架构设计要说明新功能怎样融入现有体系，以及功能内部由谁负责。使用 [架构设计模板](../templates/architecture-design.md)，按下表完成固定的四节。

| 步骤 | 必须做什么 | 输出结果（写入章节） | 进入下一步的条件 |
| --- | --- | --- | --- |
| 1. 定位置 | 查现有模块、入口和数据归属，确定新功能所在层次。 | **结论与整体架构图**：一句话结论；标出现有、新增、调整、外部模块及关系。 | 新功能边界、主要依赖和最终数据归属能在图中找到。 |
| 2. 定融入关系 | 核对复用能力、受影响的已有功能、调用方向和调整边界。 | **融入现有体系**：在整体图上标关系，用短表补图中看不清的影响。 | 重要依赖和受影响功能均有负责方。 |
| 3. 定内部职责 | 需要时放大目标功能，划分内部模块及其职责；简单需求说明整体图已足够。 | **功能架构图**：内部架构图，或“不需要细分”的理由。 | 内外图名称、连接和数据归属一致。 |
| 4. 定边界与取舍 | 说明关键选择、常见故障由谁恢复、仍需验证什么。 | **关键决定与运行边界**：简短决定表及待验证项。 | 需要确认的架构决定已确认，才进入技术方案；其余未知项标明影响。 |

**架构图是正文主体，文字是图的补充。**

| 表达内容 | 要求 |
| --- | --- |
| 整体架构图 | 纵向排列从业务能力到底层支撑的层次，横向排列同层并列能力。标明现有、新增、调整或外部模块；层次与名称以实际系统为准。 |
| 功能架构图 | 需要细分内部职责时，放大整体图中的目标功能；与整体图使用一致的名称和对外连接。 |
| 模块关系 | 连线写明依赖、调用或信息交换的含义与方向；标出最终数据由谁维护。上下左右只辅助阅读，不能代替关系说明。 |
| 文字 | 只补充图中看不出的理由、取舍、异常和待验证事项。 |
| 运行过程 | 需要时用短句或另附时序图；步骤流程图不能替代架构图。 |

图中的职责不等于必须新增服务。沿用 PRD 的概念名称，不重复定义；不列接口字段、表结构或实施清单。架构待确认时标明“建议”，确认后再写具体技术方案。

## 技术方案：怎样实现和验证

使用 [技术方案模板](../templates/technical-design.md)，按下表完成固定的七节；只写本需求涉及的内容。

| 步骤 | 必须做什么 | 输出结果（写入章节） | 进入下一步的条件 |
| --- | --- | --- | --- |
| 1. 定方案 | 查现有实现与架构设计（如有），确定核心做法、边界和关键选型。 | **方案摘要**：做法、理由、代价和待验证点。 | 方案与 PRD、已确认的架构不冲突；未确认的选择已标出。 |
| 2. 对需求 | 将每个相关 `R-xx` 对应到实现做法和验证重点。 | **需求对应**：编号映射表。 | 主要需求都有实现与验证落点。 |
| 3. 串交互 | 从用户操作画到页面反馈，写出请求、响应、常见失败和正式接口定义。 | **关键交互时序与接口**：时序图、输入与接口表。 | 正常路径和常见失败可从头追到结果。 |
| 4. 写 Web | 按页面反馈、前端逻辑与状态、接口请求的顺序写。 | **Web 技术方案**：加载、成功、失败、重试的处理表。 | 页面状态与时序图、接口结果一致。 |
| 5. 写后端 | 按接口校验、业务处理、模型与存储的顺序写，覆盖重复、冲突和中断。 | **后端技术方案**：处理表、关键模型关系与变化规则。 | 请求结果和保存结果都能由规则解释。 |
| 6. 定运行保障 | 只检查本需求涉及的环境、权限、容量、备份和恢复。 | **部署与数据保护**：运行约束及恢复办法。 | 影响交付的运行风险已有处理或待验证标记。 |
| 7. 排实施与验证 | 按可交付步骤安排实现、联调、验证与回退。 | **实施顺序与验证计划**：步骤、验证范围、回退点和待确认材料。 | 计划可执行；未实测事项没有写成已通过。 |

时序图以一次用户操作为主线，标出参与方、请求、响应和常见的失败结果。图中只画先后交互，不用它代替模块架构图；复杂处理可在 Web 或后端章节补流程图。图、Web 逻辑和后端逻辑使用相同的场景名称，读者应能从一个操作追到页面状态、接口、业务规则和保存结果。

| 层次 | 至少说清什么 |
| --- | --- |
| Web | 用户从哪里操作；前端做哪些选择、转换或临时校验；何时请求接口；成功或失败后页面如何更新。会影响最终保存结果的规则由后端判断。 |
| 后端 | 接口接受什么并如何校验；由哪个业务处理负责；读取或改变哪些模型；如何保存及返回结果。模型不等于数据库表，必要时区分业务概念与存储结构。 |
| 接口约定 | 写本方案用到的接口和输入物，链接项目中的正式定义；不在方案里另维护一份字段说明。 |

技术依据放在作出选择的段落旁，不另起重复的背景章节。没有 Web 或后端的一侧，在对应章节简要写“不涉及”；其他无关内容同样不填充。

## 交付前核对

交付前核对章节顺序，以及场景与交互、概念与属性、架构关系是否一致。按 `AGENTS.md` 精简文字，再确认关键异常、风险和待验证事项仍说得清楚。
