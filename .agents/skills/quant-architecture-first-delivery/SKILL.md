# 架构优先交付

先让人看懂新功能怎样融入现有体系、内部怎样分工，再决定如何实现。架构图标出已有和新增部分、职责边界、依赖及权威信息；文字补充关键决定、运行边界和待验证事项。图中的概念不自动对应文件、类、接口或数据库表。

本 Skill 负责架构判断与实施计划；PRD、原型、技术方案和开发仍按项目 [Skill 索引](../INDEX.md) 选择对应工作流。只推进用户要求的阶段。

## 适用范围与证据

适用于用户要求先确认架构，或需求涉及策略版本与配置、回测/交易流程、数据归属、异步任务、恢复、部署迁移、跨模块协作等，需要先确定职责边界的情况。纯文案、样式、机械接线和局部小修无需套用。

先读 `AGENTS.md`、`.agents/skills/INDEX.md`、对应需求的 PRD、现有代码、调用方和测试。技术方案若已存在也要核对；适用时查看 `docs/product/` 与对应需求的架构设计。仓库尚无实现时，以已确认的产品事实为依据；草稿和未运行验证不能写成现状。

检查现有入口、业务语义、决策者、权威数据、生命周期和失败位置。同职责优先复用。涉及外部服务、交易所规则或平台能力时，核对决定本次流程的正式资料与项目实际验证；缺乏证据的行为标为待验证，不画成已确定的调用。多个入口若汇入同一业务动作，说清汇合所需的业务事实，不因入口或后端字段不同而复制业务概念。

## 两步交付

### 第一步：架构设计

按[需求文档结构规范](../../../docs/engineering/requirement-doc-structure.md)交付图为主的架构设计，复杂度由需求决定：

1. 一句话概括架构决定和可观察结果。
2. 一张整体架构图，纵向展示从业务能力到底层支撑的层次，横向展示同层并列能力；标出功能在现有体系中的位置、复用与调整部分、外部依赖和权威信息。
3. 放大整体图中的目标功能，必要时画功能架构图，说明内部模块、职责和对外连接。
4. 用短表格补充图中难以表达的取舍、常见故障的恢复责任及关键未知项。

层次按实际系统划分；模块连线写明关系和方向，上下左右的位置不能代替说明。架构图表达边界、职责和依赖，不用步骤流程图充当主图；必要的运行过程用短句或另附时序图。此阶段不列文件、接口字段、数据表、测试命令或实现顺序。说明哪些只是概念，不要求它们成为独立组件。用户要求“先看架构”或设计尚未确认时，到这里停下，等用户确认；已有 PRD 或技术方案也不能代替这次架构确认。用户明确要求按已确认架构继续时，不重复索取确认。

### 第二步：实施计划

用户确认架构后，再从职责图倒推最小计划：要改的产物及其职责、当前必须确定的数据与协议、暂缓事项、可验收的小步骤、验证方式和回退点。计划应能追溯到已确认的职责与流程，并与现有技术方案对齐；发现冲突时先指出，按授权范围修正方案，不暗中改产品行为。

每个拟新增的文件、类、服务、接口或表都检查：当前是否有独立职责和调用方；去掉会损失什么；能否并入现有负责者。不要把只转发调用的包装层、空接口、TODO 或未来可能用到的状态做成实体。确认架构后需要实现时，转入 `quant-feature-development`；仅审视存量复杂流程时，可用 `quant-flow-review`。

## Lightning 的关键判断

- 区分策略代码版本、参数配置修订和未来一次运行的固定引用；不要把页面层级直接当成数据归属。
- 区分已保存的业务事实、页面临时输入和可重建的缓存。恢复状态必须有真实的权威来源和可达条件。
- 对回测、模拟、实盘分别指出数据、账户、订单与结果的权威方；本阶段未交付的运行能力只标为衔接点，不预建空运行框架。
- 本机到服务器的迁移应沿用已确认的稳定标识和版本关系；未经验证的安装、升级和迁移结果标为待验证。

交付前从读者角度检查：只看架构图和简短说明，能否看出功能在现有体系中的位置、内部职责、依赖、权威状态及故障责任；能否区分事实、建议与待验证事项。
