# 量化需求工作流

只推进到用户要求的阶段。文档章节按[需求文档结构规范](../../../docs/engineering/requirement-doc-structure.md)和对应模板。以 [产品愿景](../../../docs/product/vision.md)、[Roadmap](../../../docs/product/roadmap.md) 和现有需求为背景；这些文档拥有产品事实，Skill 不重复规定当前平台范围。

## 从想法到 PRD

1. 先查 `docs/requirements/`，已有需求就更新，避免重复编号；新需求从 `docs/templates/` 建立索引和 PRD。索引只放目标、状态、实际存在的产物链接和关键决定。
2. 保留原始想法，识别使用者、场景、当前问题、预期结果和已知边界。缺失信息只有影响范围或验收时才问；推断要标明。
3. 先用场景确定操作主线和成功标准，再按 PRD 模板写概念、行为、异常与验收；具体写法见文档结构规范。实现选择留给技术方案。
4. 有界面时按文档结构规范的交互设计原则做可操作原型，覆盖关键反馈状态；无界面时标“不适用”。如果任务要求效果图或视觉规范，转用 `quant-web-visual-design`。原型和 PRD 从需求索引链接。

## 从 PRD 到技术方案

职责或最终数据归属尚未确定，或用户要求先确认架构时，用 `quant-architecture-first-delivery` 先交付架构设计，确认后再细化技术方案。概念边界不自动变成类、表或服务。

技术方案先查已有实现及对应需求的架构设计（如有），再按模板写交互时序、Web 和后端实现及验证。只比较真正影响选择的方案，记录依据、实测与待验证事项。用户要求文件级计划时，列确切路径与职责，不重复 PRD。

涉及行情或交易时，只核对本需求相关的市场规则、数据权利、订单与账户状态、风控、成本和对账。分钟级时效与标的规模需要用代表性负载验证；未知的高频目标不触发提前建设。

## 交接与维护

需要单独设计测试用例时用 `quant-test-case-design`；进入代码开发时用 `quant-feature-development`；复杂链路审视用 `quant-flow-review`。更新需求行为或方案时，在授权范围内同步受影响文档；范围外先说明。

每个事实只在主文档维护一次：索引放入口，PRD 放行为，技术方案放实现，测试报告放实际结果。不要虚构批准、实测、供应商许可或法规结论。

交付前按 `AGENTS.md` 和文档结构规范核对章节、语言与关键异常；实际结果未验证时如实标明。
