# 量化平台功能开发

产品需求开发前，先读需求索引、PRD、技术方案及适用的原型或页面设计；缺少必要产物时先按 `quant-requirement-workflow` 补齐。只做用户已授权的阶段和范围。

若职责或权威数据尚未确定，先用 `quant-architecture-first-delivery` 确认架构，再制定落地计划和实现；已确认的架构不重复确认。

## 落地前

- 查当前模块、共用代码、调用方和相关测试。同职责能力优先复用；确有新责任时才在最小边界新增。对尚无应用代码的首个需求，从技术方案建立最小骨架。
- 说清本次行为、权威数据、写入方、正常结果及可达的失败。接口或持久数据变化需检查现有使用方、兼容性、迁移与回退。
- 对任务、订单、账本等异步或可重试流程，按实际风险明确重复请求、超时、重启与恢复由谁处理。不要因猜测未来高频需求预建服务或抽象。

## 开发与验证

按可验收的小功能贯通输入、业务决定、持久状态、页面反馈和验证；每个新增层必须有真实职责。优先写能揭示行为错误的测试，不写只重复实现的测试。

页面实现以已确定的交互原型和视觉设计为输入，优先使用现有组件；检查正常、空、加载、错误及禁用状态，并在目标桌面和窄窗口查看实际页面。设计有矛盾时记录并修正设计，不在代码中暗自改变产品行为。

运行受影响模块的最窄有效检查。交易或报表能力还须核对环境隔离、数据与配置版本、成本来源及结果可追溯性；只验证本次实际交付的部分。

## 收尾

按 PRD 验收项记录实际环境、执行步骤、结果和未验证项；更新需求索引与测试报告。实现偏离 PRD、设计或技术方案时，在授权范围内同步文档；范围外先说明。报告改了什么、如何验证、剩余限制，不把编译通过当作运行行为已验证。

若目标是独立审视复杂链路，使用 `quant-flow-review`；若只需设计验收用例，使用 `quant-test-case-design`。
